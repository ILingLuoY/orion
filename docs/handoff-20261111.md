## 0. 一句话现状

**稳态已经很快（rd=8 时帧间隔中位 16.7~24 ms），真正的痛点是偶发长卡（p90 35~72 ms、max 207~274 ms），根因已定位为：原版区块提交路径每帧分配 3.49 MB → G1 频繁 Young GC（845M→380M）→ 14 次 Concurrent Mark Cycle（中位 124 ms）抢渲染线程 CPU。分配不在我们代码里（capture/submit/record 合计 0.02 MB/帧）。**

下一步主方向：**接管式渲染**（见 §7），或补齐 LOD 源。

## 7. 下一步主方向：接管式渲染

### 为什么

现在是**旁挂式**：原版渲染 766 个 section（15.5 ms + 3.49 MB/帧）→ 我们再追加 RT → 全屏 blit 覆盖。**原版那份是纯浪费**（颜色被覆盖，只有深度被 `glass_alpha_blend` 等消费）。

Remix 与 Caustica 都是**替换式**：只消费一次几何（Remix 在 D3D9 层捕获网格按哈希缓存；Caustica 在区块构建阶段直接建 RT 结构），不保留原版光栅。

### 三层改造

| 层 | 要做什么 | 现状 |
|---|---|---|
| 1. 拦 draw | 保留区块几何构建（我们靠它捕获），但让 section 的 draw 不进入命令缓冲 | **未知**：`VulkanRenderPass` 只暴露 `setPipeline`/`setUniform`；`libs/` 里没有 renderpearl jar |
| 2. 自己出图 | RT 直接写最终目标 | ✅ 已有（blit 覆盖 mainRenderTarget） |
| 3. 补齐原版独占项 | GUI / 粒子 / 天气 / 手持物 | ✅ GUI pass 本就在最后 |

### 第一步（必须先做，成本 5 分钟）

反射探针：在现有 mixin 里打印 `VulkanCommandEncoder` 与 `VulkanRenderPass` 的 `getDeclaredMethods()` 签名，确认有没有 draw 级入口。

- 有 → 接管可行，工作量约 3~5 天；
- 没有 → 只能 fork renderpearl 后端（改 pipeline 状态），成本高一个量级。

### 备选路线

装 **Voxy 或 Distant Horizons**：`takeoverActive()` 才会成立，`FarFieldGate` 的现有压制机制才有意义（当前 `meshes=0`、`providing=false`、`erased=0`）。

## 8. 踩过的坑（重要）

1. **`_deploy_stale_spv.py` 不会重建缺失的 `.spv`**（`main()` 里 `if not os.path.exists(spv): continue`）。判据是**源文件内容哈希**，改 mtime 无效。删了 SPV 就得手工 `glslangValidator -V --target-env vulkan1.2 -S <stage> -e main -o <out> <src>` 补回来。
2. **`cpp/shaders` 未完全纳入 git**（`git checkout -- cpp/shaders/rgen_glossy.glsl` 报 pathspec 不存在）。改动前自行备份。
3. **`.bat` 必须 CRLF + 纯 ASCII**：UTF-8 中文注释会让 cmd 按 GBK 解析错行，报出莫名其妙的 `JAVA_HOME is set to an invalid directory`。
4. **`JAVA_TOOL_OPTIONS` 会让 `gradlew.bat` 报 `JAVA_HOME` 无效**，无法用这种方式注入 JVM 参数；走 `build.gradle` 的 `runs.client.vmArg`。
5. **`jcmd` / JFR 在 D:\RTX 上不可用**：JFR dump 恒 0 字节，jcmd attach 被拒（`AttachNotSupportedException`）。分配定位改用 `ThreadMXBean#getThreadAllocatedBytes`（已在 `FrameBudget.java`）。
6. **冷编代价**：改 `rchit` 会触发 4 条 RTPSO 全部重编（main ~688 s、k1 ~73 s、**k2d ~920 s**、k2i ~92 s ≈ 30 分钟）。缓存命中时 ~0.4 s。
7. **k2d 是编译预算最紧的一条**（曾 802 s 后 `result=-3`）；把材质 callable 换成 216 B stub 后 920 s 成功。
8. **`[PERF L10 GPU]` 需要 `ORION_PERF_TIMESTAMPS=1`**，否则 query pool 都不创建。

## 12. 二次接手（同日）：接管探针结论 + 15.5 ms 归因工具

### 12.1 探针结论：draw 级入口**存在**，接管可行（无需 fork renderpearl）

不用改代码跑游戏，直接对 `build` 里那份 renderpearl 做 javap（class 树在 `.tmp/rp/`，对应 26.3）：

| 类 | draw 级方法 |
|---|---|
| `renderpearl.frontend.FrontendRenderPass`（MC 实际持有的对象，`public class`） | `drawMultipleIndexed(...)`、`drawIndexedIndirect(GpuBufferSlice,int)`、`drawIndexed(int,int,int,int,int)`、`multiDrawIndexed(...)`、`drawIndirect(...)`、`draw(...)`、`pushDebugGroup(Supplier<String>)` —— 全部 public，可 mixin |
| `renderpearl.backend.vulkan.VulkanRenderPass`（现有 `VulkanRenderPassMixin` 已作用于它） | 同上 + `multiDrawIndexed` 直接调 `vkCmdMultiDrawIndexedEXT` |
| `renderpearl.backend.api.RenderPassBackend` | 全部 abstract，`drawMultipleIndexed` **不在**这里（它在 frontend 展开） |

⇒ §7「第一步」的答案：**有**。且本工程已有 `VulkanRenderPassMixin`（`setPipeline` HEAD 抓 commandBuffer）证明这条 mixin 通道是活的。

### 12.2 26.3 的真实地形路径（与 §7 的假设不同）

`ChunkSectionsToRender`（26.3 已改成抽象类，两个实现）才是唯一收口：

- `DrawIndirect.render()` → `setVertexBuffer(0/1)` + `setIndexBuffer` + `drawIndexedIndirect`（每桶一次）
- `DrawSeparate.render()` → `drawMultipleIndexed(draws, …)`

两条都由 `LevelRenderer.prepareChunkRenders(Indirect)?` 产出，选路由 `Minecraft.multiDrawIndirect`（默认 `true`，F3 可切）+ `multiDrawIndirectAvailable`（`maxDrawIndirectDrawCount>0 && nonZeroFirstInstance && !hints.multiDrawIndirectHasKnownIssues()`）决定。启动日志已见 `Enabling optional FeatureSet [EXT MultiDraw]`。

**这推翻了 §0 的一处推断**：若走 indirect 路径，`prepareChunkRenders` 并**不**为每个段 new `RenderPass.Draw`（那条才是逐段对象分配），所以「3.49 MB/帧来自区块提交」不能靠"766 段 × 每段 Draw 对象"解释，必须实测。

### 12.3 新增归因工具（已编译通过，默认关）

`ORION_LEVEL_PHASES=1` 打开后每 60 帧打一行，把 level 整段切成 4 块：

```
[LEVEL PHASES] n=60 indirect=true level=.. submit=.. prepChunk=.. terrainDraw=.. unaccounted=.. | max: .. | prepCalls/f=1
```

- `submit` = `LevelRenderer.submitFeatures`（实体/方块实体/破坏动画/粒子提交）
- `prepChunk` = `prepareChunkRenders` / `prepareChunkRendersIndirect`（可见段遍历 + draw group + 动态 UBO）
- `terrainDraw` = `ChunkSectionsToRender.renderGroup`（地形命令录制，**接管第一层能消掉的 CPU 上限**）
- `unaccounted` = level − 上面三项（天空 pass、frame graph 执行、OIT、云雨、手持物）

改动文件：`LevelPhaseProbe.java`（新）、`mixin/ChunkSectionsToRenderMixin.java`（新，需在 `orion.client.mixins.json` 注册）、`mixin/LevelRendererMixin.java`（+4 对 inject）。
纯读时钟，不开开关时零输出、零行为变化。

**判据（跑一局就能定）**：`prepChunk + terrainDraw` 若是 level 的 ≥50% ⇒ 接管值得做；若只有 2~3 ms ⇒ 先打 §11.2 材质（GPU 上确定的 9.12 ms），别碰接管。

### 12.4 接管式渲染第一层已落地（默认开启，`ORION_TAKEOVER=0` 关闭）

**掐点不是 draw，是 draw group 的构建**：`LevelRenderer.extractSectionDrawGroups(boolean, List, Map)` 是 `DrawIndirect` 与 `DrawSeparate` 两条路径的**共同上游**。`@Inject(HEAD, cancellable)` 直接 `setReturnValue(0)` 之后：

| 后果 | 机制 |
|---|---|
| 地形不再进命令缓冲 | 每个 layer 的 draw group 为空 ⇒ `renderGroup` 里 `if (!drawGroups.isEmpty())` 与外层 `for` 全跳过，`drawIndexedIndirect` / `drawMultipleIndexed` 一次都不录 |
| 逐段分配消失 | `sectionInfos` 不再 `add(new ChunkSectionInfo(...))`，动态 UBO 走 empty 分支（`writeDataBatched(empty)` → `GpuBufferSlice(null,0,0)`；`writeData(T[0])` → `new GpuBufferSlice[0]`） |
| 段遍历消失 | `visibleSections` 那个 766 次的循环整段跳过（含 `getRenderSectionSlice` / hash 计算） |
| auto index buffer 不再申请 | `largestIndexCount=0` ⇒ `defaultIndexBuffer=null`，`requestIndexCount` 不调用 |
| 网格构建保留 | `SectionCompiler` / `SectionMesh` / `SectionRenderDispatcher` 完全没动 —— RT 的几何捕获靠它 |
| `visibleSections` 保留 | RT 侧剔除表、`setVisibleSections` 照旧 |

**为什么不会把画面搞坏**：RT 的深度是**自己写的**——`PostFx.cpp:createDLSSDepthImage()` 建 R32_SFLOAT 的 `g_dlssDepthImage`，以 `STORAGE_IMAGE` 绑在 ray tracing 描述符 set 的 binding 7，由 rgen 在命中时写入；Java 侧 `recordFrameCommand(cmd, colorImage, w, h, …)` **从不传原版深度**。DLSS、glass_alpha_blend、NRD、god ray、VolRestir、cloud 读的都是 `g_dlssDepthView`，不是 main depth。

**安全阀**：`TerrainTakeover.active()` 要求「`rtActive` 且**上一帧**真的把画面盖进 main render target」。帧边界结算点在 `NativeVulkan.resetGuiRtState()`（每帧 `blitFromTexture` 的 finally）里、清零之前。RT 一旦某帧没出图，下一帧地形自动回来。首次进世界的前一两帧也走原版光栅。

**验证**（`ORION_LEVEL_PHASES=1`）：
1. 进世界后一行 `[TAKEOVER] terrain raster OFF (RT 已接管画面…)`；
2. `[LEVEL PHASES]` 的 `prepChunk` 落到 ~0.0x、`terrainDraw` 落到 ~0.0x，`level` 整段应减少对应量 —— **这就是接管第一层的净收益**；
3. 画面与之前一致（地形来自 RT，不是光栅）；若地形消失/HUD 正常但世界空白 ⇒ 说明 RT 没出图而安全阀失效，`ORION_TAKEOVER=0` 立刻回退；
4. 退出世界（回标题/断线）后 `[TAKEOVER] terrain raster ON …` 应出现。

**回退**：`$env:ORION_TAKEOVER="0"`（代码保留，逐帧行为与之前完全一致）。

改动文件：`TerrainTakeover.java`（新）、`mixin/LevelRendererMixin.java`（+1 个 `extractSectionDrawGroups` inject）、`NativeVulkan.java`（`resetGuiRtState` 里加一行帧边界结算）。

### 12.5 第二档：主 pass 的原版要素光栅也关掉（同一次改动内完成）

`ORION_TAKEOVER` 现在是**档位**，不是布尔：`0`=全关、`1`=只关地形、`2`=**默认**，再关主 pass 里的原版要素光栅。

掐点是 `FeatureRenderDispatcher.PreparedFrame` 的 8 个 `execute*`（全部 public、已 javap 核对）：

```
executeSolid / executeTranslucent / executeTranslucentAfterTerrain / executeOit(OitStage,RenderPass)
executeWaterMask / executeOutline / executeSeeThrough / executeAlwaysOnTop
```
统一 `@Inject(HEAD, cancellable)` → `ci.cancel()`，门控 `TerrainTakeover.skipFeatureRaster()`（档位≥2 且安全阀成立）。

**为什么视觉中性**：这些方法的唯一产物是 main render target 的像素，而那张图随后被 RT 整屏覆盖。

**为什么不会误伤**（都查过源码，不是推测）：

| 担心 | 结论 | 证据 |
|---|---|---|
| 实体/粒子几何捕获 | 不受影响 | 捕获发生在 `prepareFrame`：`FeatureRenderDispatcher.prepareFrameWithContext` 里 `group.prepare(...)` + `stagedVertexBuffer.upload()`；`execute*` 只是遍历 submit 节点发 draw |
| 手持物 | 不受影响，且**本来就已跳过光栅手** | 手走静态 `renderAllFeatures`，且 `GameRendererMixin` 有 `@Redirect` 直接不调用它（`ORION_HAND_RT=0` 才回退） |
| 屏幕特效（水下/着火/传送门） | 不受影响 | `GameRenderer.renderScreenEffects` 同样走静态 `renderAllFeatures(renderPass, frame)`，不在 `PreparedFrame` 里 |
| `PreparedFrame.close()` 的 `finishExecute` / `stagedVertexBuffer.endDraw()` | 安全 | `FeatureRenderer.finishExecute` 是 default 空实现，`close()` 无条件下调用；`endDraw` 配对的是 `prepareFrame` 里的 `upload()`，没被拦 |

**顺带新增的归因**：`FeatureRenderDispatcher.prepareFrame` 单独计时（`[LEVEL PHASES]` 里的 `featurePrep`），它是「3.49 MB/帧」最可疑的分配源 —— 每帧重建 `PreparedGroup` 列表 + 写动态顶点缓冲。这一笔我们**不能**跳过（几何就是从这儿读走的），但必须知道它多大，才能判断要不要继续拆。

**没做的（有意）**：`executeClassicTransparency` 里的 `cloudRenderer / weatherEffectRenderer / worldBorderRenderer` 光栅没拦。理由：它们在 GPU 分解里合计 <0.3 ms（`[PERF L10 GPU]` 的 cloud 是 RT 自己的云 pass，不是这条），而每拦一个就要多一个 mixin 目标，收益不成比例。

### 12.6 关于「冷编代价」的一句澄清

本次全部改动是**纯 Java（mixin + 普通类）**，不碰任何 `.glsl`/`.spv`、不改 SBT、不改 RTPSO 的 key ⇒ **零冷编**，也没有 RTPSO 缓存失效。重启客户端就是缓存命中（~0.4 s）。所以这轮可以放心反复重启做 A/B（`ORION_TAKEOVER=0/1/2` 三次重启就能把档位收益量干净），不需要一次赌对。

**一次运行能拿到的全部数字**（`ORION_LEVEL_PHASES=1`）：

```
[TAKEOVER] terrain raster OFF …            ← 安全阀翻转
[LEVEL PHASES] n=60 indirect=? takeover=2 level= submit= featurePrep= prepChunk= terrainDraw= unaccounted= | max: …
```
`level − (submit + featurePrep + prepChunk + terrainDraw)` = 天空 + frame graph 执行 + 云雨 + 其余；对比 `takeover=0/1/2` 三档的 `level` 差值就是每一档的净收益。

### 12.9 拆开 `featurePrep`：里面**几乎全是我们自己的实体捕获**

新增探针（`ORION_LEVEL_PHASES=1` 会多打一行 `[LEVEL PHASES FEAT]`）：

- `SubmitNodeStoragePhaseMixin` → `drainPhases`（sort）
- `PreparedGroupPhaseMixin` → `PreparedGroup.prepare`（featGroup），并按 `FeatureRendererType.name()` 分桶
- `StagedVertexBufferPhaseMixin` → `upload()`
- `ModelFeatureRendererMixin` 里直接给我们自己的 `EntityRtCapture.beginModel/endModel` 计时（`ours(capture)`）

rd=8 实测（`craftcollection2`，四窗口）：

```
featurePrep=26.15  sort=0.01  featGroup=25.88  upload=0.24  rest=0.01
                   ours(capture)=19.49
                   Entity Model=20.25  Item=5.26  Block Model=0.16  Text=0.14  Particle=0.07
```

另一窗口：`featurePrep=33.01 featGroup=32.41 ours=16.62 Entity Model=17.39 Item=14.36`。

**结论（三条，都改变了原来的判断）**：

1. `sort` / `upload` / `rest` 全在 0.01~0.6 ms，**`featGroup` 就是 `featurePrep` 的全部**（99%）。
2. `featGroup` 按类型分：**Entity Model 17~20 ms + Item 5~15 ms**，方块实体 / 文字 / 粒子都 <0.3 ms。
3. **`ours(capture)` 16.6~19.5 ms ≈ Entity Model 桶的 96%** ⇒ 这段 CPU 不是原版在磨，是**我们自己的 `EntityRtCapture.beginModel/endModel`（含 `uploadBatch` 的 JNI）**。原版模型顶点构建的净成本只有 1~4 ms。

⇒ 下一步优化目标非常明确：**实体捕获路径**（每模型两次 JNI + `uploadBatch`），而不是原版渲染、也不是接管。
`Item` 桶（5~15 ms）目前**没有**打我们的计时（物品走 `RenderTypeFeatureRendererMixin`，未插桩），很可能同样以我们的捕获为主，需要下一步补测。

### 12.11 逐顶点捕获的真实规模（2026-11-11 收尾，含一次自造崩溃的教训）

新增 `verts/f` 计数后实测（rd=8、同一张物品密集地图）：

```
featurePrep=152.73  Item=124.32(max 184.99)  Entity Model=24.61
ours(capture)=24.2  ours(generic)=39.31  mtn=11.34  jni=20.17
verts/f = 1,360,554
```

⇒ **每帧 136 万个顶点**进我们的捕获。对照 §12.10 的 A/B（捕获关掉时 `Item` 只剩 41~77 ms），
我们的逐顶点环节成本 ≈ **35~61 ns/顶点**；其中 `uploadBatch` 里 MV 计算 11.3 ms（≈8 ns/v）
和 JNI 20.2 ms（≈15 ns/v）是另外可单独量出来的两笔。

**所以「按模型批量提交」的真正价值不在于省掉 hook 调用本身**：每顶点 12 个 float（48 B）的
格式转换 + 每 quad 6 次 emit 是硬成本，1.36M 顶点就是 65 MB/帧的写入（这也解释了
`[RT GEOMETRY SLOW]` 里 `stagingMB=222`）。要真降下来，得减少**顶点数量**或减少
**每帧重复转换**——例如静态物品（展示框里的物品）几何缓存成一批、形态不变时直接复用。

⚠ **踩坑（当次即回滚并修好）**：把逐顶点入口的 `ThreadLocal.get()` 换成全局静态镜像后，
**区块网格构建的工作线程也会调 `captureVertex`**，它们看到了渲染线程正开着的批次并往里塞顶点，
`pendingQuadVertexCount` 顶过 4 ⇒
`ArrayIndexOutOfBoundsException: Index 20 out of bounds for length 20`
（`crash-reports/crash-2026-11-11_20.47.52-client.txt`）。
修法：`ActiveBatchSlot.owner` 记录归属线程，`captureVertex` 只在
`owner == Thread.currentThread()` 时直读镜像，否则回落 `ThreadLocal`。

### 12.12 结论修正：卡的区域不是「每顶点效率」，是**图元数量**（2026-11-11 定论）

加了 `submits/f` 计数后的实测（同地图，物品密集区）：

```
featurePrep=218.87  Item=190.30(max 225.27)  Entity Model=22.91
verts/f=1,949,140   submits/f=486,664 (item=486,543  model=121)
ours(capture)=22.55 ours(generic)=56.45 mtn=16.50 jni=29.13
```

另一窗口：`submits/f=588,817 (item=588,750)`、`verts/f=2,357,217`。
而同一张图的轻区域只有 `verts/f≈143,590`、`Item≈17`。

⇒ **卡的区域每帧有 40~59 万次 item/自定义图元提交、约 200 万顶点**（平均每次提交 4 顶点 = 一个 quad）。
对比：轻区域 14 万顶点、`Item` 17 ms。**这是纯数量问题**，所以之前盯 ns/顶点、盯 hook 开销都打不到点上。

天花板很清楚：

| 项 | 该区域实测 |
|---|---|
| 原版 `ItemFeatureRenderer.prepareGroup`（捕获关掉后仍在） | 41~77 ms |
| 我们逐顶点捕获（`Item` 增量） | 50~80 ms |
| C++ 侧为这些几何重建 TLAS | `staging 222 MB/帧`、`geometry 70 ms` |

**真正能落地的两条（都要求「静态图元不重复转换」）**：

1. **静态物品几何缓存**：展示框/展示盒里的物品不随时间变，按 `(itemModel, pose, texture)`
   缓存顶点块，命中就跳过逐顶点转换与 JNI ⇒ 省我们那 50~80 ms。
2. **接管 Item 链**：画面来自 RT，原版那份 item 顶点是纯浪费。跳过
   `ItemFeatureRenderer.prepareGroup` 的原版写顶点、直接用缓存喂 RT ⇒ 再省 41~77 ms。
   两条合起来能把该区域的 190 ms 压到接近 0。
3. 配套：静态物品应「一次建 BLAS、之后只改实例变换」，而不是每帧重建 —— 当前几何管线是
   每帧从捕获顶点重建，这一条比前两条更大。

#### 12.12.1 缓存键探针的第一轮结果：**锚点选错了**

加了 `itemKeys/f` / `hit%` 探针（挂在 `ItemFeatureRenderer.prepareSubmit`）：

```
submits/f=653,107 (item=653,027)   itemKeys/f=5   hit%=100.0   verts/f=2,614,556
Item=285.22(max 359.12)  ours(capture)=14.77  ours(generic)=81.46
```

**矛盾**：`getVertexBuilder` 每帧 65 万次（`beginCustomSubmit` 计数），
但 `prepareSubmit` 每帧只跑 ~5 次 ⇒ **26.3 的物品顶点不是由 `prepareSubmit` 产生的**
（它只处理特殊情形），缓存锚点必须换。

⇒ 下一步锚点候选：`RenderTypeFeatureRenderer.Group`（`getVertexBuilder` 返回的就是
这个 group 的 consumer）。可在 `getVertexBuilder` 里取到 `currentGroup()` 的 identity
与 `renderType`，按 `(group 身份, renderType)` 统计 distinct 与重复率，
再决定缓存粒度是按 group 还是按 renderType。

`ORION_LEVEL_PHASES=1` 打开即可看到这两个字段，探针本身不改行为。

#### 12.12.2 第二轮探针（`getVertexBuilder`）：粒度确定了 = **25 个 group**

```
vb/f=640,293   groups/f=25   vbPerGroup=25,374.9   (rtypes 极少，整数除法显示 0)
Item=290.09(max 389.43)   verts/f=2,563,728   ours(generic)=79.17
```

读法：每帧 **64 万次** `getVertexBuilder`，但它们只落在 **25 个 consumer** 上
（`getVertexBuilder` 返回的就是当前 group 的 consumer，25 个 consumer ≈ 25 个 group）
⇒ **每个 group 平均被调用 2.5 万次**，正好是「每 quad 一次」。

⇒ **缓存粒度 = group，不是 submit、也不是 renderType。**

落点：`RenderTypeFeatureRenderer.prepareGroup(FeatureFrameContext, List<Submit>, boolean)`
（`calls/f=11.75`，即每帧 12 个 group prepare）。那里拿得到该 group 的整个 submit 列表，
可以：(a) 用 `(列表 identity, size, 首/末 submit identity)` 做键；(b) 命中就
`ci.cancel()` 跳过原版写顶点、直接复用上次捕获的顶点块 —— 一次同时消掉
原版 41~77 ms 和我们 50~80 ms。

**注意**：`ItemFeatureRenderer.prepareSubmit` 那条路已证明不是物品顶点来源（每帧 ~5 次），
不要再往那个方向做键。

#### 12.12.3 第一阶段实现完成：键定了，但还不够（2026-11-11）

`ORION_ITEM_CACHE=1`（默认关）启用的实现：

- `RenderTypeFeatureRendererMixin`：`prepareGroup` HEAD 算 group 键 → `EntityRtCapture.beginGroup(key)`；
  RETURN → `finishGroup()`（回放或登记，然后照常 flush）。
- `EntityRtCapture`：命中 ⇒ `captureVertex` 直接返回（整组不跑逐顶点转换），
  flush 前把上一帧的顶点块 `put` 回批次并修正 `vertexCount`；
  未命中 ⇒ 正常转换，flush 前把本批顶点块拷进缓存。
- 安全阀：只对 `ItemFeatureRenderer` 生效；只缓存 `uvMapping==null && !projectiveUv`；
  回放前校验 `textureSlot` 一致 + 缓冲容量；缓存有 256 MB / 96 条硬上限
  （第一版没上限，**把堆打爆过一次**：`OutOfMemoryError: Java heap space`）。

**键的三次迭代（都是实测）**：

| 键 | 命中 |
|---|---|
| `identityHashCode(submits)` | 0/106 |
| `submits.hashCode()`（List 内容） | 0/142 |
| **逐字段语义键**：pose 矩阵分量 / displayContext / light / overlay / outline / tint 内容 / quad 数 + 首个 BakedQuad identity / foil | **70/60（≈54%）** |

原因很清楚：`Submit` 虽是 record，但 `pose`（`PoseStack.Pose`）、`tintLayers`（`int[]`）、
`quads`（`List`）走的全是 identity 哈希 ⇒ 前两种键每帧都变。

**但这一阶段没拿到收益**：`Item` 仍 216 ms、`ours(generic)` 仍 57.7 ms。
因为这一版**只跳过我们自己的逐顶点转换，原版仍在写顶点**——那 41~77 ms 一分没省。
要兑现，必须进入第二阶段：命中时**同时 `ci.cancel()` 掉 `prepareGroup`**，
此时 vanilla 不再调 `getVertexBuilder`、不会开批次，所以回放要自己
`acquireBatch(entry.textureSlot, …)` 建批次再灌字节，然后 `endCustomGroup()` 收尾。

另外：这张 collection 地图在默认 ~1 GB 堆下启动期偶发 OOM（与缓存无关，加载期就炸）。
功能验证用 `gradlew runClient -Pxmx=4G`（build.gradle 里新增的可选 `-Pxmx`，
**做性能 A/B 时不要带它**，否则帧间隔/GC 口径不可比）。

#### 12.12.4 第二阶段：跑通了，但撞上 group 级缓存的架构上限

实现（`ORION_ITEM_CACHE=1`）：命中时 `ItemFeatureRenderer.buildGroup` 直接 `ci.cancel()`
（不写原版顶点），并用缓存顶点 `acquireBatch` + `replayStandalone` 自建批次上传。

⚠ **取消点不能放 `prepareGroup`**：它无条件 `groups.add(currentGroup)`，而
`executeGroup(groupIndex)` 用下标取同一列表。在 HEAD 取消 ⇒
`IndexOutOfBoundsException: Index 1 out of bounds for length 1`
（`crash-2026-11-11_21.35.19-client.txt`）。取消 `buildGroup` 则组照常入列、只是 `draws` 为空，
`executeGroup` 循环走 0 次 —— 安全。

实测（rd=8、物品密集区，无崩溃）：

```
gc h/m/x = 120/60/0            ← 每帧 2 命中 / 1 未命中
ours(generic) = 11.5 ms        ← 对比开启前的 57 ms，**我们的转换耗时降了 ~80%**
Item = 254~261 ms              ← 但总耗时**几乎没动**（开启前 240~290）
```

**原因**：一个有 3000 件物品的 group，只要**里面任何一件**的键变了（掉落物在自转 ⇒
pose 每帧变；或附魔光效动画），整组键就变 ⇒ 整组 miss。而最贵的那一组恰好每帧都在变。
group 级缓存是「全有或全无」，在这种混合内容下拿不到收益。

⇒ 结论：group 级缓存的架构上限已经到顶。要继续只能换粒度：
**(a) 把 `buildGroup` 里的 submit 循环按 submit 分段缓存**（需要自己重写这段遍历），
或 **(b) 直接做第 3 条（native 侧静态几何不重建）+ 只对"完全静止"的 group 启用缓存**。

### 12.13 C++ 侧几何上传/重建现状（2026-11-11 读码 + 实测）

#### 通道

`Entities.cpp`：

| 入口 | 作用 |
|---|---|
| `beginEntityFrame` | 清空 `g_entityFrameVertices / g_localPlayerFrameVertices / g_handFrameVertices` 与对应 motion 数组 |
| `uploadEntityBatch` | 每个 Java 批次 append：顶点 `+= 相机世界位置`（转回世界空间）、`materialId=0`、把 `textureSlot` 写进 `pad2`、`pad1` 编码归属（0 普通/−1 自发光/+1 本地玩家/+2 手部） |
| `endEntityFrame` | 对三层各做**整层 FNV 哈希** → 与 `g_entityCachedHash` 比 → 变了才 `g_chunkMeshes[LAYER_KEY]` 整层 swap 并 `g_entityRebuildRequested = true` |

#### 三条关键事实

1. **判等粒度是「整层」，全有或全无。** 一件掉落物在自转（pose 每帧变）⇒ 整个 entity 层 107 MB 顶点全部重传 + BLAS 重建。
   这与 §12.12.4 里 group 缓存撞上的是同一个结构性问题，只是发生在 C++ 侧。
2. **每帧固定成本：整层哈希 32~34 ms。** `[PERF L10 STALL] tag=entityFrameVertexHash` 在 rd=8 物品密集区有 **4933 条**告警，ms≈32~34。
   根源是 `hashVertexPayload` 是**单条串行依赖链**（每个字依赖上一次的 `hash *= prime`，乘法延迟 3~5 cycle 全串起来；107 MB ≈ 1340 万字）。
   **已修**：改成 4 路独立累加后合并（语义只用于自比较，输出值变但不影响判定）。
3. **重建节流存在但不够**：`Frame.cpp:1806` 对 `g_entityRebuildRequested` 有 2 帧节流（`ORION_DYN_REBUILD_INTERVAL`），节流窗口内重建被推迟而不丢弃。但一旦到期就是 `rebuildWorldGeometry` 全量遍历 section + 全表 sort + TLAS BUILD。

#### `stagingMB=222` 与 `pCap=54ms` 的含义

- `totalStagingBytes`（`WorldGeometry.cpp:831/1150`）累计**本帧要重建/refit 的段**顶点字节；222 MB = 该帧确实重传了这么多段的顶点。
  refit 路径（三角形/顶点数不变）**同样整段重传顶点**，所以"只改了位置"并不省上传。
- `pCap` = `perfL10RebuildStart → rtxPreLoopMarkLog`，即重建前置段（等 section 锁 / 发布本帧捕获段），源码注释写的「等区块锁」。

#### 哈希并行化的验证（2026-11-12 08:20 一局）

- `[PERF L10 STALL] tag=entityFrameVertexHash`：**0 条**（改前同一探针 4933 条，ms 32~34）。
- 但这一局**不在重场景**：玩家在 `(28.5, 0, 36.5)`，峰值 `verts/f=286,630`；
  而之前的重场景是 `(162.09, 22.24, 124.61)`、`verts/f≈2.2~2.6M`（差 8~9 倍）。
  原因是此前几局崩过，存档位置没写回，quickPlay 落到了别处。
- 该局顶点规模下旧实现约 4 ms（13.7 MB / 170 万字 × 2.4 ns），**高于 3 ms 阈值 ⇒ 会打 STALL**；
  新实现 0 条 ⇒ 已确实低于阈值。
- 但重场景的**绝对收益尚未直接测到**。按串行依赖打掉 4 路估算，32 ms → 8~10 ms，
  即 **约省 22~24 ms/帧**。要精确测需要站回 `(162, 22, 124)` 那一带（进游戏 `/tp`）。

#### 子层切分已实现（`ORION_ENTITY_LAYER_BUCKETS`，默认 1 = 逐位旧行为）

改动点（共 4 处，都很小）：

1. `OrionInternal.h`：新增 `ENTITY_RT_LAYER_INDEX`、`isEntityRtLayerKey()`、`entityRtBucketKey(b)`。
   桶键不能用加法（`ENTITY_RT_SPATIAL_KEY` 低位全 1，+1 会进位到 layer index），
   所以 **b=0 用原键、b>0 用 `ENTITY_RT_SPATIAL_KEY - b`**。
2. `Geometry.cpp`：`layerEntry.first == ENTITY_RT_LAYER_KEY` → `isEntityRtLayerKey(...)`，
   这样每个桶都走 `split.entity` 分支。
3. `Entities.cpp`：新增 `updateEntityLayerBucketed()` —— 按 `textureSlot % K` 把本帧顶点
   （连同 motion）分成 K 份，**每桶独立哈希 + 独立判等 + 独立换入 `g_chunkMeshes[bucketKey]`**，
   motion 也跟着桶发（否则 MV 错层）。
4. `endEntityFrame`：`useBuckets` 时跳过整层哈希/整层换入，`changed` 由 `bucketChanged` 驱动。

实测：**buckets=8 与 buckets=1 都能正常进世界、无崩溃**。

但**没拿到干净 A/B**：两局顶点规模不同（8 桶局 1.33M、1 桶局 91 万），
说明分别处在不同加载阶段；`geometry` 的 66~92 ms 尖峰只出现在 1 桶局的加载期，
不能直接归因。**需要同位置同阶段对照**（等加载稳定后各跑一局，比较晚段窗口）。

# 13. 【接手用】实例化第 1 步：SSBO 实例矩阵（2026-11-12 交接）

> 目标：让命中着色器能用**自己的 SSBO 矩阵**做实例变换，从而给「一个模型多个实例」铺路。
> 这一步**不改任何行为**：矩阵全部填单位 ⇒ 画面必须逐位不变，这就是验收标准。

## 13.1 为什么必须走 SSBO，而不是内置 builtin

`gl_ObjectToWorldEXT` 在本工程实测**不可用**：把它乘进顶点位置后，整个 RT 画面变成
「黑 + 彩色噪点」（顶点被压成一点、三角形退化，降噪器在空输入上出噪点）。
三次独立验证（SPIR-V 1.6 与 1.5 都试过），只要换回旧 `.spv` 立刻恢复正常。
⇒ **结论：不要再用这个 builtin。** 改用我们自己的 SSBO 矩阵表。

## 13.2 关键设计约束：`instanceCustomIndex` 要拆着用

shader 里顶点地址是这样取的：

```glsl
sectionVertexAddressBuffer.vertexAddresses[gl_InstanceCustomIndexEXT + gl_GeometryIndexEXT]
```

而实例矩阵也需要一个 per-instance 索引，hit 阶段能拿到的只有这一个 index。
⇒ **必须拆分**：建议 `高位 20 bit = 顶点槽位`、`低位 12 bit = 矩阵槽位`，
shader 两处各取一半；C++ 发实例时按此编码 `instance.instanceCustomIndex`。
（`SECTION_VERTEX_ADDRESS_SLOT_LIMIT = 1 << 18`，20 bit 够用。）

矩阵格式建议 **3 × vec4 = 48 B**（行主序，第 4 列是平移），SSBO 里用 `vec4 m[]`，
每实例占 3 个 vec4，取用 `vec3(m[i*3+0].xyz… )` 自行组装，避免 std430 对 `mat4x3` 的填充歧义。
